# Análisis Funcional — API de Gestión de Usuarios

## Módulos identificados

### Módulo de Autenticación
- Gestión de tokens de acceso y control de sesión.

### Módulo de Usuarios
- CRUD de usuarios:
  - Crear, consultar, actualizar y eliminar lógicamente usuarios.
  - Gobernanza de acceso diferenciada por roles.

### Módulo de Perfiles
- Manejo de datos extendidos del usuario como biografía, foto y preferencias de notificación.

---

## Actores y Roles

### ADMIN
- Acceso total a todos los endpoints.
- Capacidad de gestionar usuarios (crear, modificar y eliminar cualquier usuario).

### USER
- Acceso restringido únicamente a consultas y modificaciones de su propio perfil.
- No tiene permisos para eliminar cuentas ni listar a todos los usuarios.

### GUEST
- Solo puede acceder al endpoint de autenticación `POST /api/auth/login`.

---

## Flujos por módulo

### Flujo principal — Módulo de Autenticación (Login)
1. `POST /api/auth/login` recibe email y password.
2. Validar si el email existe.
3. Comparar el password con el hash almacenado.
4. Verificar que el usuario tenga `active = true`.
5. Generar y retornar `accessToken` (24h) y `refreshToken` (7 días).

#### Flujo alternativo
- **Credenciales inválidas:** Responder HTTP 401 con mensaje "Credenciales inválidas".
- **Usuario inactivo:** Responder HTTP 403 con mensaje "Cuenta deshabilitada. Contacte al administrador".

---

### Flujo principal — Módulo de Usuarios (Creación)
1. `POST /api/users` (ADMIN required) envía datos del nuevo usuario.
2. Validar unicidad del correo electrónico.
3. Validar formato y complejidad del password.
4. Encriptar el password usando bcrypt (salt rounds: 12).
5. Crear registro con `active = true`.
6. Responder HTTP 201 con objeto del usuario (sin incluir el password).

#### Flujo alternativo
- **Email duplicado:** Responder HTTP 400 con el mensaje de error apropiado.
- **Password no cumple reglas de negocio:** Responder HTTP 400.

---

### Flujo principal — Módulo de Perfiles
1. `PUT /api/users/:id/profile` recibe datos para actualizar (foto, biografía, preferencias).
2. Validar autenticidad del usuario (token válido).
3. Verificar autorización adecuada (USER puede modificar solo su perfil; ADMIN cualquier perfil).
4. Actualizar la información del perfil del usuario.

#### Flujo alternativo
- **Token inválido o expirado:** Responder HTTP 401 con el mensaje de error.

---

## Reglas de negocio

- **RN-001:** El email debe ser único en el sistema.
- **RN-002:** El password debe tener al menos 8 caracteres, una mayúscula y un número.
- **RN-003:** Usuarios con `active = false` no pueden autenticarse.
- **RN-004:** Al realizar `POST /api/auth/logout`, el `refreshToken` es invalidado.
- **RN-005:** Un usuario con rol ADMIN no puede borrar su propia cuenta.
- **RN-006:** La paginación máxima permitida en la lista de usuarios es de 100 por página.

---

## Precondiciones globales

- Todos los endpoints (excepto `POST /api/auth/login`) requieren un header: `Authorization: Bearer <accessToken>`.
- Formato esperado de la API: `Content-Type: application/json`.
- Todas las fechas se manejan en formato ISO 8601 UTC.

---

## Ambigüedades detectadas

⚠️ No se especifica el comportamiento al intentar renovar un `refreshToken` expiratado mediante `POST /api/auth/refresh`.

⚠️ No está claro si el endpoint `PUT /api/users/:id` permite cambiar el rol del usuario. Esto podría tener implicaciones críticas de seguridad.

⚠️ No se ha documentado un límite de intentos fallidos de login ni una política de bloqueo automático de la cuenta.

⚠️ No se especifica el comportamiento en caso de intentar realizar una acción con un token explícitamente invalidado (después de `logout`).

⚠️ No se menciona cómo manejar la eliminación lógica (active = false) respecto a datos del perfil en el módulo de Perfiles.

---

## Resumen ejecutivo

La API de Gestión de Usuarios implementa tres módulos principales: Autenticación, Usuarios y Perfiles. Estos módulos están orientados a las necesidades de un sistema con roles establecidos como ADMIN, USER y GUEST, promoviendo buenas prácticas de seguridad mediante el uso de tokens JWT y cumplimiento de reglas de negocio claras, como la unicidad del email y la complejidad de contraseñas.

Sin embargo, se encuentran ambigüedades importantes que afectan casos críticos como la renovación de tokens expirados, el límite de intentos fallidos de login y la definición de roles en actualizaciones de usuarios. Estas lagunas representan un riesgo a la consistencia y seguridad del sistema, y deben ser resueltas antes de avanzar con la implementación.

El diseño actual cumple la mayoría de los requisitos funcionales básicos, pero algunas áreas requieren mayor especificación para prevenir futuros errores o vulnerabilidades operativas.
