# Análisis Funcional — API de Gestión de Usuarios

## Módulos identificados

1. **Módulo de Autenticación**
   - Funciones relacionadas con el inicio y cierre de sesión, así como la renovación de tokens de acceso.

2. **Módulo de Usuarios**
   - Operaciones CRUD sobre usuarios, con restricciones basadas en roles y reglas de negocio específicas.

3. **Módulo de Perfiles**
   - Gestión de información adicional como foto de perfil, biografía y preferencias.

---

## Actores y Roles

1. **ADMIN**
   - Acceso completo a todos los endpoints.
   - Puede crear, listar, modificar y eliminar usuarios.
   - Restricción: No puede eliminar su propia cuenta.

2. **USER**
   - Acceso limitado a sus propios datos personales y perfil.
   - No tiene permisos para listar ni eliminar cuentas de usuarios.

3. **GUEST**
   - Solo tiene acceso al endpoint de login.

---

## Flujos por módulo

### Módulo de Autenticación

#### **Flujo Principal: Login**
1. El cliente envía una solicitud `POST /api/auth/login` con `email` y `password`.
2. El sistema verifica:
   1. Que el email exista.
   2. Que el password coincida con el hash almacenado.
   3. Que el usuario esté activo (`active = true`).
3. Si las validaciones son correctas:
   - Se genera y retorna un `accessToken` con 24 horas de validez.
   - Se genera y retorna un `refreshToken` con 7 días de validez.
4. El cliente almacena ambos tokens.

#### Flujo alternativo: Credenciales inválidas
- **Condición:** Email no existe o password incorrecto.
- **Respuesta:** HTTP 401 con mensaje "Credenciales inválidas".

#### Flujo alternativo: Usuario inactivo
- **Condición:** Usuario tiene `active = false`.
- **Respuesta:** HTTP 403 con mensaje "Cuenta deshabilitada. Contacte al administrador".

---

### Módulo de Usuarios

#### **Flujo Principal: Creación de Usuario**
1. Un ADMIN envía una solicitud `POST /api/users` con los datos del nuevo usuario.
2. El sistema realiza las siguientes validaciones:
   1. Que el `email` no exista previamente.
   2. Que el `password` cumpla con los requisitos mínimos de seguridad.
3. Se hashea el password utilizando `bcrypt` con 12 salt rounds.
4. Se crea el usuario con `active = true`.
5. Respuesta: HTTP 201 con el objeto del usuario creado (sin incluir el password).

---

#### Otros Endpoints:

1. **GET /api/users**
   - Lista todos los usuarios (solo ADMIN, con soporte de paginación).

2. **GET /api/users/:id**
   - Retorna los detalles de un usuario por ID.

3. **PUT /api/users/:id**
   - Modifica los datos de un usuario especificado por ID.  
   ⚠️ Ambigüedad: No se especifica si este endpoint permite cambiar el rol del usuario.

4. **DELETE /api/users/:id**
   - Realiza la eliminación lógica (cambia `active` a `false`).
   - Restricción: Los ADMIN no pueden eliminar su propia cuenta.

---

### Módulo de Perfiles

1. **GET /api/users/:id/profile**
   - Retorna la información extendida del perfil del usuario (foto, biografía, preferencias).

2. **PUT /api/users/:id/profile**
   - Permite actualizar la foto de perfil (almacenada en S3), la biografía y las preferencias de notificación.

---

## Reglas de negocio

1. **RN-001:** El `email` debe ser único.
2. **RN-002:** El `password` debe tener al menos 8 caracteres, una mayúscula y un número.
3. **RN-003:** Los usuarios eliminados (con `active = false`) no pueden autenticarse.
4. **RN-004:** Al hacer logout, el `refreshToken` debe invalidarse.
5. **RN-005:** Un ADMIN no puede eliminar su propia cuenta.
6. **RN-006:** La paginación tiene un límite máximo de 100 registros por página.

---

## Precondiciones globales

1. Todos los endpoints (excepto `POST /api/auth/login`) requieren autenticación mediante el header:
   ```
   Authorization: Bearer <accessToken>
   ```

2. La API utiliza y retorna datos en formato `application/json`.

3. Todas las fechas se manejan en formato estándar ISO 8601 UTC.

---

## Ambigüedades detectadas (⚠️)

1. ⚠️ **Renovación de refreshToken expirado:** No se especifica el comportamiento del endpoint `POST /api/auth/refresh` si el `refreshToken` ya expiró.

2. ⚠️ **Cambio de roles de usuario:** No se explica si el endpoint `PUT /api/users/:id` permite modificar el rol de un usuario.

3. ⚠️ **Restricción sobre intentos de login:** No se menciona si existe un límite para los intentos fallidos de inicio de sesión ni si se bloquean cuentas por seguridad.

---

## Resumen ejecutivo

El documento describe una API RESTful para la gestión de usuarios que se compone de tres módulos principales: autenticación, usuarios y perfiles. La API distingue claramente las capacidades y restricciones según diferentes roles (ADMIN, USER, GUEST). En términos de seguridad, emplea tokens JWT para autenticar a los usuarios, requiere credenciales con validaciones específicas y establece reglas para la gestión de usuarios y sus datos.

No obstante, se identificaron algunas ambigüedades relevantes:
1. La falta de definición del comportamiento frente a un `refreshToken` expirado.
2. La incertidumbre sobre si el rol de un usuario puede ser modificado a través de un endpoint.
3. La ausencia de reglas en caso de múltiples intentos fallidos de login.

Estos puntos deberían ser aclarados para asegurar la correcta implementación y uso de la API.
